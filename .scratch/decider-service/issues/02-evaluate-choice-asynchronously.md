# 02: Evaluate Choice asynchronously

**What to build:** Let clients submit named Choice questions against shared State and receive calibrated choices and probabilities without a slow backend blocking other callers. Preserve the requested names and labels, expose the actual configured Decider identity, and report the backend work attributable to the request.

**Blocked by:** 01: Discover configured Decider models.

**Status:** ready-for-agent

- [ ] `POST /v1/systemone` evaluates one or several named Choice questions through real public validation, model resolution, pinned Decider preparation, awaited backend HTTP, and upstream answer assembly. Successful responses have the required `model`, `answers`, and `usage` structure; explicitly enabled aliases resolve to the actual configured Decider identity.
- [ ] Accept text, object, and array State; permitted structured instructions and criterion descriptions; and permitted omitted/null instructions and null Choice descriptions. Reject null State, Choice label arrays, missing required fields, empty questions, invalid question types, unknown models, configured request-limit violations, and unsupported option capacity with field-oriented 422 errors. Retain contract validation for other question types as their evaluation paths are added.
- [ ] Preserve criterion order, model-specific prompt layout, option neutralization, and independent questions using the pinned Decider implementation. Each remote row contains exactly one final answer slot. Check every complete rendered prompt plus its one-token prediction allowance against configured backend context capacity; reject excess without truncating State or allowing context shifting to discard evidence.
- [ ] Use a shared lifecycle-managed `httpx.AsyncClient` for llama.cpp's native `/completion` endpoint. Forward the caller's TypeSafe bearer key only to the configured backend, keeping it local to the request across all rows and eventual coverage retries; never mutate shared client authentication or default headers, or substitute an operator probe or development key. Adapt preparation, awaited evaluation, and assembly explicitly rather than merely replacing a synchronous engine method. Offload sufficiently expensive synchronous preparation so it does not monopolize the event loop; close the client on shutdown.
- [ ] Send raw token IDs with one prediction, `temperature=-1`, pre-sampling probabilities, neutral penalties, disabled sampling filters, disabled prompt caching, and non-streaming responses. Read final-slot `probs[0].top_logprobs`, match alternatives by token ID, and apply the configured Choice temperature exactly once. Generated text is not a decision answer.
- [ ] Preserve upstream Choice selection and confidence semantics. Require complete option coverage, finite probabilities within zero to one, and an approximately-one sum using a tolerance justified by pinned assembler rounding. Until coverage recovery is delivered, missing alternatives or malformed backend probabilities fail with a sanitized 502 rather than invented values or partial success.
- [ ] Keep preparation state, results, and token accounting local to each request. Sum required backend input/output counters across all attributable rows, including repeated State processing; reject missing or malformed required counters instead of inventing zero usage. Counter interpretation remains subject to selected-build verification.
- [ ] Public HTTP checks use controlled backend distributions while retaining real preparation, calibration, and assembly. Verify labels and identity, structured inputs, validation and context limits, complete responses or errors, exact multi-row usage totals, and unchanged Choice results when questions are added or reordered. Concurrent callers with different bearer keys retain their own key on every backend row without cross-talk; keys never enter prompt or request-body content. Use deterministic backend gates to demonstrate that slow inference leaves unrelated requests responsive.
